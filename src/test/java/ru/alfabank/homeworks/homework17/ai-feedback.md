# Обратная связь по архитектуре проекта (homework17)

Задание 17 — API-тесты для ServeRest (https://serverest.dev). Стек: Java, Gradle, JUnit 5 (Jupiter), RestAssured, Jackson (DTO), Hamcrest.

## Что сделано хорошо

- **Чистое разделение тестов и моделей.** DTO (`Usuario`, `Produto`, `LoginRequest`, `CarrinhoRequest`) вынесены в отдельный пакет `models/`, что упрощает переиспользование и сериализацию тел запросов через Jackson. Использование Lombok `@Data` сокращает boilerplate.
- **Базовые настройки в `@BeforeAll`.** `baseURI` и логирование ответов при падении валидации заданы один раз — это упрощает чтение тестов и отладку.
- **Изоляция расширенных тестов.** Новые тесты выделены в отдельный класс `ServeRestExtendedTest`, что не ломает существующий happy-path сценарий и позволяет запускать их независимо.
- **Cleanup через `@AfterAll`.** Отслеживаются созданные пользователи и товары для последующего удаления (учёт связи товар↔токен).

## Что стоит улучшить

1. **Зависимость от общих live-данных ServeRest.** Проект тестирует общую базу, где данные разделяются между всеми пользователями API. Это главный источник хрупкости (реальный кейс: `shouldGetAllProducts` падал из-за чужого товара с пустым именем). Рекомендация:
   - минимизировать проверки, зависящие от конкретных значений чужих записей;
   - создавать собственные данные в каждом тесте и удалять их после.

2. **Порядок выполнения тестов.** В `ServeRestTest` используется `@TestMethodOrder(OrderAnnotation)` — тесты полагаются друг на друга через общие статические поля (`userId`, `token`). Это снижает надёжность: если один тест упадёт, последующие могут дать ложно-негативный результат. Лучше строить тесты так, чтобы они не зависели от порядка (уникальные данные в каждом тесте + автономный cleanup через `@AfterEach`/`@AfterAll`).

3. **Дублирование тела запроса вручную.** Часть тестов строит JSON-строки конкатенацией. Надёжнее передавать DTO-объекты (как уже сделано для `Usuario`), чтобы избежать ошибок экранирования и упростить поддержку.

4. **Хардкод URL.** Пути вида `/usuarios/{_id}`, `/carrinhos` разбросаны по тестам. Целесообразно вынести в константы/helper, чтобы при изменении API править в одном месте.

5. **Отсутствие уровня абстракции поверх RestAssured.** Тесты напрямую обращаются к `given()...`. Для расширяющегося набора методов есть смысл добавить тонкий слой (например, классы-репозитории `UsuariosApi`, `ProdutosApi`, `CarrinhosApi`), что повысит читаемость и уменьшит дублирование кода.

6. **Сборка (`build.gradle`).** Есть неиспользуемые зависимости в контексте задания 17 (Cucumber, datafaker, jfiglet). Они не мешают, но их наличие размывает предназначение модуля. Можно ограничить состав или оставить с комментарием о назначении.

7. **Согласованность акцентов в сообщениях.** ServeRest возвращает акцентированные португальские строки (`Já existe produto`, `Não foi encontrado`). В исходнике важно сохранять точные значения, чтобы ассерты не падали из-за разницы в кодировке/акцентах.

## Резюме

Архитектура простая и понятная, подходящая для учебного задания. Главные риски — связность тестов через порядок выполнения и зависимость от общих данных внешнего API. Приоритетные улучшения: автономность тестов, вынос URL в константы/helpers и (опционально) тонкий слой-обёртка над API. Все 26 тестов зеленые.
